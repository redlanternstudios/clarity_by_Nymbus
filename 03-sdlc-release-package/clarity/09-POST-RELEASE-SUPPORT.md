# Post Release Support

## Hypercare

- Launch enters a defined hypercare window
- Monitoring is tighter during rollout
- Support volume, routing accuracy, and unresolved cases are watched closely
- Any repeated confusion in borrower copy or queue routing is treated as a release signal, not a user problem

## Internal Chatbot

- Classifies incoming tickets
- Suggests routing destination
- Flags ambiguous or high severity cases
- Does not fully resolve complex issues
- Human confirmation remains required before route finalization

## Routing Targets

- Floor support queue
- Customer support queue
- Product review queue
- Technical escalation queue

## Sustainment

- Product owns issue prioritization
- Support owns daily handling and categorization
- Engineering owns defect follow-up
- Leadership owns launch visibility and go/no-go decisions

## Operating Cadence

- Review open tickets, routing errors, and unresolved borrower questions
- Review the source copy for any notice language causing repeat confusion
- Check that the repo, Kiro mirror, and Drive copies still match
- Update the changelog when the package changes

## Exit Criteria

- Ticket routing is stable
- No critical blockers remain open
- Teams understand the support model
- Hypercare can safely step down
